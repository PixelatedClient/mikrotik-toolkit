## A cloud VPC is still a network

Every major cloud provider offers a private virtual network — AWS calls it a VPC (Virtual Private Cloud), Azure a Virtual Network (VNet), Google Cloud a VPC Network — and despite the marketing name, the underlying ideas are the ones already covered in this course:

- **Subnets** carve the VPC's address range into smaller ranges, usually one per availability zone or tier, the same subnetting math from the Foundations track.
- **Route tables** decide where traffic goes, conceptually identical to a router's routing table, just presented through the provider's console or API instead of a RouterOS CLI.
- **Security groups / network security groups** are stateful firewalls attached to instances or subnets — the cloud version of the firewall chain concepts from the MikroTik Operations track, minus the explicit connection-state tracking syntax.

The main practical difference from a physical network: almost everything is provisioned through an API or console instead of console cable and CLI, and the underlying physical switches and routers are the provider's, never visible or directly configurable.

## Connecting a VPC to somewhere real

A cloud network is only useful once it can talk to an office, a data centre or another cloud. Three common approaches, in order of typical cost and reliability:

- **Site-to-site VPN**: an IPsec tunnel (Network Security track) over the public internet between the cloud provider's VPN gateway and an on-premises router. Cheapest, quick to set up, subject to internet path variability.
- **Direct connect / express route / cloud interconnect**: a dedicated private circuit from the customer's network to the cloud provider, bypassing the public internet entirely. Higher cost and lead time, but stable bandwidth and latency — the choice for production workloads sensitive to either.
- **VPC peering / transit gateway**: connecting two VPCs (same provider, sometimes same or different accounts) directly, without traversing the public internet, or via a hub-and-spoke transit gateway when many VPCs need to reach each other and a full mesh of individual peerings would be unmanageable.

## Hybrid connectivity in practice

A common real pattern: production workloads split between an on-premises data centre and one or more cloud regions, connected by a direct-connect-style private circuit for the steady baseline traffic, with a site-to-site VPN as a cheaper backup path if the primary circuit fails. This mirrors the primary/backup routing patterns already covered in the Advanced Routing track — the cloud path is just another next hop with its own metric.
