## What is a packet?

Data never travels as one big blob. It is chopped into small chunks called **packets**. Each packet carries a header (who sent it, who should get it) and a payload (a slice of your data).

## Why does data need to find its way?

Your phone is not directly wired to YouTube's servers. Between you and them sit dozens of routers. Each router looks at a packet's destination address and decides the **next hop**. This is **routing**.

## The 7 layers of OSI (simple version)

The **OSI reference model** (ITU-T X.200, the same document published jointly as ISO/IEC 7498-1) defines seven layers, each built on the one below it:

1. **Physical** – the transmission medium itself: cables, fibre, radio, electrical signals.
2. **Data link** – reliable transfer across one physical link, including framing and physical (MAC) addressing.
3. **Network** – routing and logical addressing between different networks (this is where IP sits).
4. **Transport** – end-to-end delivery, flow control and error checking between two endpoints.
5. **Session** – establishing, managing and ending a dialogue between two communicating applications.
6. **Presentation** – data formatting, encryption and translation so different applications can understand each other.
7. **Application** – the layer applications themselves use to access network services (HTTP, DNS, and so on).

Real-world networking rarely names all seven separately. **RFC 1122**, which specifies the requirements for Internet hosts, describes the Internet protocol suite as four layers instead: Link, Internet, Transport and Application — and it explicitly notes that its Application layer "combines the functions of the top two layers — Presentation and Application — of the OSI reference model." This course mostly uses OSI's own three lower layers (Physical, Data Link, Network) by name, since they map directly onto real, separately-troubleshootable problems (a bad cable, a switching loop, a routing mistake), and groups everything above Transport into "the application," in the same spirit as RFC 1122's simplification.

## How your phone talks to YouTube

1. Phone asks DNS: "what is the IP of youtube.com?"
2. Phone opens a connection to that IP over TCP, or over **QUIC** — a transport protocol, defined in RFC 9000, that carries its packets inside UDP datagrams rather than using TCP directly (this is why network tools sometimes show YouTube traffic as UDP, not TCP).
3. Packets leave via your Wi-Fi, reach your ISP's router, cross several networks, and arrive at Google — each router along the way makes its own next-hop decision, so a packet's exact path is not fixed in advance.
4. Video packets flow back toward the phone; since each router forwards independently, the return path is not guaranteed to be the exact reverse of the outbound one.
