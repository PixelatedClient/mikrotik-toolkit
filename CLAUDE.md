# Network Academy

Free, static networking-education site. Astro 7 + React islands + Tailwind v4. Courses are MDX; interactive tools are React components backed by pure TypeScript libs. No backend, no database.

## Commands

- `npm run dev` - dev server
- `npm run build` - static build to `dist/` (must pass before any deploy)
- `npm test` - Vitest, pure-logic tests in `tests/`

## Layout

- `src/content/courses/<track>/NN-slug.mdx` - lessons. Frontmatter: `title`, `track` (see the enum in `src/content.config.ts`), `module` (e.g. `2.1`), `order` (per-track, consecutive), `duration`, `summary`. Schema in `src/content.config.ts`; adding a track means updating the enum there AND `src/data/tracks.ts`.
- `src/lib/subnet.ts` - IPv4 math (CIDR, split, VLSM). Shared by the calculator and the config generator.
- `src/lib/mikrotik.ts` - RouterOS v7 `.rsc` generator: `DEVICES`, `validate()`, `generate()`. Roles: `gateway`, `isp-edge`, `vlan-switch`.
- `src/lib/vlan.ts` - VLAN designer engine: addressing plan (`10.<id/256>.<id%256>.0/24`), switch and router script generation (reuses `generate()`), and `trace()` which explains a ping. `src/data/labs.ts` - lab catalogue; each lab's configs live in `public/labs/<lab id>/`.
- `src/lib/stp.ts` - spanning tree engine (root election, root/designated/alternate ports, failure, partitions) behind the Spanning tree lab; proven against hand-computed cases, 300 random topologies, and the rstp-triangle lab files. `src/lib/bgp.ts` - BGP best-path engine and the BGP lab missions (pure, tested). `src/lib/trainer.ts` - subnetting question generator.
- `src/components/` - React islands: `SubnetCalculator`, `ConfigGenerator`, `BgpLab`, `BgpSession`, `SubnetTrainer`, `PacketJourney`, `Challenge`, `VlanDesigner`, `StpLab`, `LabChecklist` (and the static `LabDiagram.astro`). Use `client:load` on tool pages and `client:visible` when embedded in a lesson. Lessons embed them from MDX (`import X from '../../../components/X'`); any new component must be added to `COMPONENTS` in `tests/content.test.ts`.
- `src/layouts/Base.astro` - header, footer, theme toggle, SEO tags. All pages use it.
- `src/scripts/progress.ts` - per-browser lesson progress in localStorage.
- `public/labs/` - downloadable lab configs.

## Conventions

- Style with the semantic Tailwind tokens defined in `src/styles/global.css` (`bg-bg`, `bg-surface`, `border-line`, `text-fg`, `text-muted`, `text-accent`). Do not hardcode colours; dark mode works by swapping the CSS variables under `.dark`.
- Keep logic out of components: put it in `src/lib/` with a test in `tests/`.
- MDX code blocks for RouterOS use plain fences (Shiki has no RouterOS grammar).
- Anything that runs in the browser must tolerate blocked `localStorage` / clipboard (see `progress.ts`, `ConfigGenerator.tsx`).

## RouterOS rules (generated and taught configs)

- Target RouterOS **v7** syntax only (`/routing bgp connection`, `/routing filter rule`, `/routing ospf interface-template`).
- VLAN filtering is enabled **last** in any bridge script, to avoid lockouts.
- Generated configs must always include: input-chain drop-by-default, invalid-drop, service hardening. ISP edge adds BGP in/out filters, anti-spoofing, and a blackhole anchor route.
- Changing generator output means updating `tests/mikrotik.test.ts` and any lesson snippet that quotes it.

## Deploy

Static site, targets Vercel (`vercel.json` sets security headers and cache). Set `SITE_URL` to the real domain at build time: it drives canonical URLs, the sitemap and `robots.txt`. Default is the placeholder `https://networkacademy.example`.

## RouterOS syntax provenance

Generator and lesson syntax was cross-checked against MikroTik's v7 documentation: BGP connection properties (`as`, `router-id`, `local.role`, `output.network`, `output.filter-chain`, `input.filter`), routing-filter rules (`dst ==`, `dst in`, `dst-len`, `set bgp-*`; default chain action is reject), OSPF, WireGuard, SNMPv3, traffic-flow (v5/v9/IPFIX), wifi CAPsMAN and IPv6 DHCP PD. `type=ptp` is confirmed on a device (7.16 accepts `type=ptp`, rejects `point-to-point`). BFD `min-rx`/`min-tx`/`multiplier` units are confirmed on a device (see below). Only the 7 labs have been run on a device so far.

## Verified on real RouterOS 7.16 (GNS3 CHR, 2026-09-21)

All 7 labs were loaded onto CHR 7.16 nodes and their verify steps and most tasks run (interface names remapped to the physical wiring; PCs were stand-in CHRs). What real RouterOS taught us:

- `passive` on `/routing ospf interface-template` is a bare flag: `passive=yes` is a syntax error; clear it with `!passive`. Fixed in labs, lessons and NOC noc-11.
- `lo` is a built-in interface, so `/interface bridge add name=lo` fails; labs use a bridge named `loopback`.
- BFD: `use-bfd=yes` alone leaves the session inactive ("BFD forbidden for interface"). A `/routing bfd configuration add interfaces=... min-rx=200ms min-tx=200ms multiplier=5` entry is required; the `ms` units are confirmed.
- `/routing bgp instance` does NOT exist on 7.16 (`bad command name instance`). 7.16 uses `/routing bgp template add name=... as=... router-id=...` and `templates=` on each connection. **Still used by `src/lib/mikrotik.ts` (line ~290), the BGP labs and BGP lessons; decision pending.** BGP sessions are named `<name>-1` on 7.16.
- Firewall: traffic to the router's own IP is judged in the input chain, not forward. Removing a forward "accept established" rule breaks nothing unless the chain ends in a drop-all.
- WireGuard: a running peer keeps its learned endpoint (editing the endpoint is masked; re-create the peer). Wrong endpoint and wrong key look identical in the peers table. wg0 MTU 1420.
- GNS3 does not propagate a disabled port's link-down to the far end; silent failures (BGP hold timer 3 min, STP 34 s vs RSTP 3 s, OSPF dead timer) are real, which is why BFD matters.
- Config generator: all outputs for hEX and hAP ax2 profiles (gateway, isp-edge, vlan-switch) import with zero errors on a fresh 7.16 CHR once the factory default DHCP client is removed (the header now says to start from a no-defaults router). The BGP style is selectable: template (7.16-7.19, default) or instance (7.20+, not verified on a device).
- Reference commands: all 34 run on 7.16; cmd-12 needs the OSPF area to exist first (note added). `as=` directly on a `/routing bgp connection` is also accepted.
- NOC incidents: 1, 2, 3, 4, 5, 6, 7, 8, 10, 11, 12 reproduced on 7.16 and their RouterOS outputs replaced with real formats. Incident 5 was wrong as written (a router that also initiates the BGP connection still comes up when 179 is dropped on input; an unestablished session shows no entry at all, not `state=Active`) and was rewritten. Incident 9 (CGNAT) needs a real upstream and is still illustrative, as is all PC-side output.
- Lesson snippets: all 39 lessons with code were run line by line on a clean 7.16 CHR (277 command lines: 197 accepted, 43 skipped as unsafe/interactive, 22 context-dependent, 13 flagged and triaged as non-lesson causes such as `sfp-sfpplus1` not existing on a CHR or storm control needing a real switch chip). Real lesson bug found and fixed: the QoS queue-tree `up-voip` line needs `max-limit`. This proves syntax acceptance only, not the behaviour the prose describes.
- Engines and tools checked against real 7.16 behaviour: routing engine (longest prefix beats distance: a /24 at distance 200 wins over a /16 at distance 1; an off-link next hop leaves the route inactive; connected beats static for the same prefix; link down removes the route; no route gives `net unreachable`), firewall engine (first match wins, no match accepts, `drop` gives silent timeouts and `reject` returns an ICMP `net unreachable`), administrative distances (0/1/20/110/115/120/200, all confirmed), spanning tree engine (4-switch square with default priorities and again with one link cut: root, root path costs and all port roles match; the far end of a cut link stays up in GNS3), BGP best-path engine (7 attribute scenarios incl. MED compared only within the same neighbour AS: all match), VLAN designer (generated router and switch scripts import clean; all 9 ping outcomes match `trace()`), subnet maths (60 random prefixes match the router's `/ip address` network). Finding: `set bgp-med` in an OUTPUT filter on a locally originated prefix was not advertised on 7.16 (set attributes in the receiver's input filter instead; prepend in an output chain does work).
- NOT verified on a device: PPPoE MSS clamp effect, SNMPv3/traffic-flow/IPv6 PD behaviour (snippets are syntax-checked only), CAPsMAN/wifi (needs radios), storm control (needs a switch chip), NOC incident 9 (needs a real CGNAT upstream), BGP reject-own-prefix and `input.limit-process-routes-ipv4`, generator outputs for rb4011/ccr2004/crs326.

## Accounts, locks and the retro layer

- **Accounts** are optional and use Supabase (`supabase/schema.sql`, `.env.example`, README "Accounts"). Without `PUBLIC_SUPABASE_URL` / `PUBLIC_SUPABASE_ANON_KEY` the built site has no login button, every visitor is a guest, and locked pages say accounts are not switched on. In `npm run dev` without those variables a **demo mode** keeps accounts in the browser so the flow can be tried; that code is compiled out of production builds (`DEMO` in `src/scripts/auth.ts`). Still to build: social login.
- **Password reset and self-service deletion** (`src/scripts/auth.ts`: `requestPasswordReset`, `updatePassword`, `deleteAccount`; UI in `AuthBar.tsx`'s "Forgot your password?" link and the signed-in menu). A reset email lands the visitor back on the site with a Supabase recovery session; `onAuthStateChange`'s `PASSWORD_RECOVERY` event fires `RECOVERY_EVENT` (`src/scripts/session.ts`), which the header catches to open a "set a new password" dialog (also reused for "change password" while already signed in). Deletion calls the `delete_own_account()` Postgres function in `supabase/schema.sql`: `security definer`, but hard-wired to `auth.uid()`, so it can only ever delete the caller's own row — the anon/authenticated client has no direct delete access to `auth.users`. The delete dialog requires typing DELETE before the button enables, matching the confirm-before-destructive-action rule.
- **`delete_own_account()` is live on the real project and verified end to end (2026-09-22):** applied via a transient DB-password script (deleted immediately after, same handling as the original schema run — no credential ever written to a file). Verified with a real disposable account: signed up over the Auth REST API, confirmed its email directly in `auth.users` (password-grant signup needs a clicked email link otherwise, which this project has turned on), logged in for a real access token, called the RPC with it (204), then confirmed a second login attempt with the same credentials failed (400) — the account and its `progress` row are genuinely gone, not just locally signed out. The anon key alone (no user token) also calls the RPC successfully but as a harmless no-op, since `auth.uid()` is null with no real session and the delete then matches zero rows.
- **What is locked for guests** (rules in `src/lib/features.ts`, tested in `tests/auth-logic.test.ts`): Route Ridge and Firewall Fortress, NOC incidents of level 2 and 3, the daily challenge, badges, and saved progress. Lessons, tools, labs, the reference, Subnet Valley, easy incidents and topic practice stay free. Locks are a progress gate, not security: the content is static and public. Gating lives in `src/components/game/Gates.tsx` (`LevelRunner`, `NocRunner`, `PracticeRunner`), `LockPanel`/`LockChip` in `src/components/auth/`, and the world map.
- **Sync** (`src/lib/sync.ts`, `src/scripts/auth.ts`): on login the browser's progress and the account's are merged with "keep the better value" rules (repeat-safe, order-independent, never loses progress), badges the player already qualifies for are awarded retroactively, and later changes upload after 1.5 s. Badges are only awarded while logged in (`src/scripts/game-store.ts`). Logging out clears local progress so shared computers stay clean; it stays on the account.
- Anything that opens a dialog from the header must be **portalled to `<body>`**: the header uses `backdrop-filter`, which traps `position: fixed` descendants. The header must also stay `sticky` with `z-index: 40` (an older rule had silently made it `relative; z-index: 1`).
- **Retro layer** (end of `src/styles/global.css`): zero border radius everywhere (theme radii are 0), pixel-font nav and section headings, CSS-drawn carets (Press Start 2P has no arrow or square glyphs), a colour strip under the header, terminal-style code blocks, light CRT scanlines (`body::after`, off for `prefers-contrast: more`), blinking title cursor (motion-safe only).
- Verified in Chrome (Playwright, scripts not in the repo): full guest, lock, login, unlock, save, logout, restore flow (32 checks); axe-core reported zero WCAG 2.1 AA violations in dark and light on the main pages and with the dialog open; no horizontal overflow at 390 px. **Verified against a real Supabase project (2026-09-22):** `.env` holds a real project URL and publishable key, `supabase/schema.sql` was run against it, and a full browser test signed up, logged in, synced a real quiz result to the `progress` table (checked with a direct REST query), restored XP/level/streak/badges on a fresh login, and logged out cleanly (local state cleared, header updated). The legal pages (`terms.astro`, `privacy.astro`) now carry a real contact address and email.

## Browser lab simulator (`/labs/<id>`, "IN BROWSER")

Learners configure virtual routers on the website instead of using GNS3. **It is a simulator, not real RouterOS**: a small RouterOS-flavoured CLI on top of our own network engine, with behaviour and output copied from real RouterOS 7.16 captures.

- `src/lib/sim/`: `ip.ts` (addresses, time format), `table.ts` (RouterOS table layout: flags legend, index column, D slot, right-aligned numbers, multi-line cells, wrapped blocks), `device.ts` (interfaces of type ether/loopback/bridge/vlan, addresses, routes; connected + static routes with the real active/inactive rules; lookup = longest prefix then distance; bridges, ports, VLAN table, DHCP pools/servers/leases, learned MACs), `l2.ts` (layer 2: spanning tree over all bridges via `computeStp`, and `segment()`, which follows a frame across cables and bridges applying pvid, frame-types, the bridge VLAN table with vlan-filtering, tagged/untagged egress, blocked ports and loop detection), `menus-l2.ts` (`/interface` with bridge and vlan types, `/interface bridge` + `port` + `vlan` + `host` + `monitor`, `/interface vlan`, `/ip pool`, `/ip dhcp-server` + `network` + `lease`), `firewall.ts` (first match wins, no match accepts, negation, port lists, connection-state, connection-nat-state), `network.ts` (cables and the hop-by-hop packet walk: un-NAT of replies, dst-nat, input/forward/output chains, TTL, routing, ICMP errors, src-nat, and ARP-style next-hop resolution across the whole broadcast domain including switches; `pingOnce`, `tcpConnect`, `traceroute`, `dhcpDiscover`), `cli.ts` (tokenizer, unambiguous abbreviations like `addres=`, `[find where ...]`, contexts, tab completion, real error texts with columns), `commands.ts` (`/ping`, `/tool traceroute`, `/tool fetch`, `/export`), `index.ts` (PC/VPCS commands, prompt), `lab.ts` (checks, build/replay).
- Supported commands are listed in `SUPPORTED` (cli.ts): `/system identity`, `/interface` (+ bridge, bridge port, bridge vlan, bridge host, vlan), `/ip address|route|service|pool|dhcp-server|firewall filter|firewall nat`, `/ping`, `/tool traceroute|fetch`, `/export`; PCs understand `ip`, `dhcp`, `show ip`, `ping`, `trace`. Eight labs from the catalogue and lesson-only labs run in the browser: three-router, nat-port-forward, inter-vlan-routing, rstp-triangle, ospf-triangle, bgp-basics, wireguard-basics, plus the smaller lesson labs in `lessonLabs.ts`/`lessonLabsMore.ts`. Not supported yet: OSPF areas beyond the backbone, BGP route reflection/communities beyond what bgpFilter.ts covers, and WireGuard's own handshake/encryption (see the sections below). `bgp-two-isp` (multi-AS, 4 routers) stays GNS3-only.
- Labs are data in `src/data/simLabs.ts` (routing/NAT) and `src/data/simLabsSwitching.ts` (VLANs, spanning tree) (topology comes from `labs.ts`, so the diagram and GNS3 wiring stay the same): setup commands, tasks with automatic `checks` (`ping` (`@PC3` = that PC's current address), `tcp`, `address`, `pc`, `pc-in`, `route`, `ran`, `bridge`, `bridge-port`, `bvlan`, `stp-root`, `stp-root-port`), hints and a reference solution. `tests/sim-labs.test.ts` proves no task is done at the start and each solution completes its task in order without CLI errors.
- UI: `src/components/sim/SimLab.tsx` and `Topology.tsx`. The learner's typed commands are saved in localStorage (`na-sim:<labId>`) and replayed on load; tasks award XP once through `recordLevel` (`lab-<labId>-<taskId>`), and 5 finished tasks earn the "Lab Rat" badge.
- Fidelity evidence: `tests/sim-cli.test.ts` pins error messages, columns and table layouts to captured real output; `tests/sim-network.test.ts` pins routing, firewall and NAT behaviour that was verified on real routers (TTL 63 across one router, longest prefix beats distance, drop vs reject, drop-all input kills router pings, masquerade, port forward, refused vs timeout).
- Switching evidence (captured on real 7.16 routers first): error texts (`failure: device already added as bridge port`, `value of vlan-range out of range (1..4094)`, `failure: interface cannot be in tagged and untagged at the same time`, the multi-line invalid-interface message), the bridge/port/vlan/host/monitor/lease layouts, DHCP handing out the highest free pool address first, the automatic "added by pvid" VLAN entry, and `set [find ...]` reporting `no such item (4)` when the selection also holds a dynamic entry. `tests/sim-l2.test.ts` pins these and checks the spanning tree roles/failover and loop behaviour against the real triangle and ring results.
- Known differences from real RouterOS (switching): spanning tree converges instantly (real RSTP took about 3 s after a silent failure, classic STP about 34 s); with `protocol-mode=none` any loop just makes traffic vanish instead of a real broadcast storm; BPDU guard does not trip; bridge port `learning`/`forwarding` flags are simplified; frames are always flooded (MAC learning only fills the host table); no MSTP, no port-cost or priority per port.
- Known differences from real RouterOS: pings default to 4 (the real tool runs until Ctrl-C), traceroute prints only the final table, `/ip firewall` has no interface lists or address lists, the `H` hw-offload flag is not shown, times are simulated, a disabled interface takes the far end down too (like hardware, unlike GNS3), and `Script Error:` prefixes on missing arguments were only observed over SSH.
- To add a browser lab: add an entry to `SIM_LABS` for a lab in `labs.ts` that uses only routers and PCs; the test suite then checks it.

## Sources policy (important)

Every lesson is `status: draft` (default) or `status: sourced`. A sourced lesson lists at least two `sources` (title, https url, publisher, `accessed` date) and `verifiedAgainst`, ends with a `## Check yourself` section, and every fact in it must have been read on the cited page. `tests/content.test.ts` enforces the shape, not the truth, so the truth is on you:

- Read the page itself (a search snippet is not enough), and only cite pages you read. If a page is unreadable, do not cite it.
- Check dates. Old material (the 2016 MTCNA outline, the 2009 MPLS slides) decides *which topics matter*, never a command or figure.
- Paraphrase. Do not copy text, diagrams or videos, and do not embed third-party video (a test forbids iframes and video tags). Cisco Networking Academy, NetworkLessons and MikroTik training are copyrighted: use them only for topic coverage.
- Mark our own design advice as such (see "our design guidance" in the PPPoE lesson).
- `src/data/roadmap.ts` holds the step-by-step plan shown on `/roadmap`; `/sources` explains the policy and lists every citation automatically.
- **Step 8 is done (2026-09-22): every one of the original 33 draft lessons (Foundations, MikroTik, Advanced Routing, ISP Operations) is now `sourced`,** alongside the MikroTik Operations and Layer 2 in Depth tracks sourced in an earlier session — 47 lessons in total, the entire original curriculum. Sources used: ITU-T X.200, RFC 768, 792, 1035, 1112, 1122, 1812, 1918, 2131, 2328, 2516, 2827 (BCP 38), 2865, 2863, 3411, 4271, 4291, 4456, 4632, 4890, 5880, 6177, 6480, 7011, 7761, 9000, 9293, WireGuard's own protocol page, MANRS's network operator guide, PeeringDB, sFlow.org/Wikipedia's sFlow page, Wikipedia's burstable-billing page, the BGP table-size tracker at bgp.potaroo.net, and around 20 MikroTik RouterOS documentation pages. One GPON lesson's optical specs (line rates, wavelengths, budget classes) were checked against a secondary summary rather than the ITU-T G.984.2 PDF directly, because that PDF would not extract as readable text (unlike X.200, which did) — flagged in the lesson itself rather than silently citing an unread page. Where a lesson was mostly this project's own operational guidance rather than a documented rule (the ISP edge and ISP-scaling checklists, the troubleshooting method, GPON provisioning/fault-guide practice), it says so explicitly, matching the PPPoE lesson's "our design guidance" convention.
  - Corrections the real sources forced: RFC 1122 only merges Presentation+Application into the Internet model's Application layer, not Session too; a /24's "usable = total − 2" convention isn't in RFC 4632 itself; the wifi package covers "Wi-Fi 5 wave2 and newer," not specifically "Wi-Fi 6"; the BFD lesson's "BGP hold time 90s by default" was wrong for RouterOS — the real default is 3 minutes (confirmed both in MikroTik's own BGP docs and this project's own earlier GNS3 testing), 90s is a different vendor's convention, not a protocol requirement; the IPv6 lesson's flat "/56 residential, /48 business" framing is an operator convention, not something RFC 6177 itself mandates (it explicitly rejects a one-size-fits-all rule).
  - Still `draft`: the four newer tracks added 2026-09-22 (Security, Automation, IPv6/Wireless, Cloud/DC) plus MPLS and VPN Services — 20 lessons, none yet checked against real sources.
- Fetch tips: long help.mikrotik.com pages are truncated by the fetch summariser. Download `https://help.mikrotik.com/docs/exportword?pageId=<id>` with curl and read the text (it is a MIME/HTML export). Never trust a search snippet for a fact.
- Shell caveat: this repo's bash tool strips one level of backslash escapes and chokes on `!` inside heredocs. Use the Write/Edit tools for regexes, `
` and RouterOS lines containing `!`.

## Conformance harness (`tools/conformance/`, local only, never shipped)

Runs the same command script on the simulator and on the real CHR 7.16 routers in GNS3 (project "test", 7 routers; wiring and management IPs in `lab.json`), masks timings/MACs/dates, and diffs the output. **This is how the browser CLI is kept faithful to real RouterOS: capture first, then fix the simulator to match.**

- `node tools/conformance/run.mjs [scenario ...] [--sim-only] [--save] [--mark-gaps]` (needs `python` + `paramiko`; set `MSYS_NO_PATHCONV=1` in Git Bash). `real.py` resets every router it uses to a bare config before and after (ether8, the management port, is never touched) and waits 0.8 s after firewall commands (rules show the `I` flag until compiled, which is noise).
- Scenarios are JSON in `scenarios/`: `devices`, `steps: [device, command, "warm"?]`. `"warm"` steps run but are not compared (ARP warm-up pings). Scenarios so far: routing-basics, export-all, detail, survey, empty, fwprops, fworder.
- `--save` stores the real output in `<name>.real.json`; `--mark-gaps` writes `<name>.gaps.json` (steps where the simulator still differs). `tests/conformance.test.ts` replays every scenario offline: matching steps must keep matching, listed gaps are skipped, and a gap that starts matching FAILS the test until you re-run `--mark-gaps` (so the list only shrinks). Tests never talk to GNS3.
- Comparison rules live in `normalize.mjs` (`same()`): timings, MACs, dates, `H` flag, dynamic-servers masked; `print detail` compared as a word stream with link-time and link-downs removed; row numbers ignored for `where` prints (real numbering is not positional); spacing differences compared loosely (real tables size columns from the whole table).
- **Traps that locked routers during this work:** never add `chain=input` drop/reject rules without an `in-interface=` that excludes ether8 (SSH dies); a fasttrack rule creates a dynamic "special dummy rule" that survives until reboot and makes `remove [find]` fail (use `[find where dynamic=no]`); an unscoped `chain=input action=drop` in a scenario locks the router out. Recover through the GNS3 console (telnet 192.168.221.128:<port>, ports 5000..5012) or stop/start the node via the GNS3 API (http://192.168.221.1/v2, admin/admin, project a049e178-...).
- Real-router findings now in the simulator: `reject-with` picks the ICMP code; a router's own address answers even when its port is unplugged; `where` supports `~` (regex); prefix error `value of netmask out of range (0..32)`; `/export` (whole router, per menu, `terse`) with real section order, alphabetical properties, 78-column wrapping with backslash continuation; `print detail` for address, route, service, interface, bridge, port, vlan table, vlan, pool, dhcp server/network, address-list, interface list; `/ip route` print shows routing-table, immediate-gw, scope, target-scope, local-address; `/ip service` columns (empty ones dropped), `api-ssl` enabled by default; DHCP lease default 30m and the `I` flag on servers whose interface has no address; bridge port `I` flag when the port is down; firewall rules accept the full property set with real print order and real validation errors (`failure: ports can be specified if proto is tcp,udp,udp-lite,dccp,sctp`, `failure: tcp-flags works only with tcp`, port range 0..65535, custom chains are allowed), address lists and interface lists (`src/dst-address-list`, `in/out-interface-list` match), `/interface ethernet print`, `/system resource|clock|package`, `/user print`, `/ip dns print|set`, `/tool ping`.
- Known gaps (see the `*.gaps.json` files): `print as-value`, `get`, `value-list`, `:put` expressions and variables, `unset`, `/ip route add` without a gateway is accepted by real RouterOS, `/ip arp`, `/interface print stats`, `/ip neighbor`, `/log print`, NAT rule details (the `I` flag, netmap/same/redirect print), mangle/raw menus, queues, scripts. OSPF, BGP and WireGuard are now supported (see the sections below); their own small remaining gaps are listed there.
- `where` now also supports `or` (`cli.ts`'s `parseConds`/`whereHit`: `and` binds tighter, matching documented RouterOS precedence, e.g. `dst-address=A or dst-address=B`) and firewall filter/NAT rules support `move [numbers] destination=N` and `comment [numbers] (comment=text | "text")` (2026-09-22). All three verified against the live GNS3 CHR 7.16: `empty.json`'s captured real output was stale (more scenario steps had been added since it was last saved, desyncing every step after the divergence point — re-captured with `--save`, not just `--mark-gaps`, which is why a scenario's own `.real.json` must be current before trusting its gaps). Real 7.16 findings while fixing this: `comment` accepts `comment=text` as a named argument (not only the bare positional form assumed at first); `unset` is a recognised action but `unset 0 comment` specifically fails with `input does not match any value of value-name` on this menu, so `unset` stays unimplemented and in the gaps list rather than guessed at. **Caution for next time:** `--sim-only --mark-gaps` writes an *empty* gaps file (sim-only mode never loads the saved real output to compare against) — never combine those two flags; use `--mark-gaps` alone (hits the live router) or fix a stale `.real.json` with `--save --mark-gaps` first.
- New scenarios added for OSPF, BGP and WireGuard: `ospf.json`, `bgp.json`, `wireguard.json`. The BGP and WireGuard routers needed a clean `/routing bgp connection`/`/interface wireguard` removal added to `real.py`'s reset list, or state leaked from one capture into the next (a stale peer, a stale dynamic filter rule) and produced confusing diffs.
- **The Security track's `secure-management-basics` lab locked itself out on a live test (2026-09-22).** Its own drop-by-default input-chain rules (`chain=input action=drop ... src-address=!10.0.5.0/24`, then a final `chain=input action=drop`) are exactly the CLAUDE.md-documented ether8 trap: run against a real router over the harness's own SSH connection, the rule drops the harness's management session the instant it is added, because the harness's source address is not inside the lesson's admin subnet. Recovered via the GNS3 console (telnet), confirmed all 4 firewall rules and the 3 service-disable lines are accepted, correctly ordered RouterOS 7.16 syntax with no errors, then cleaned up and restored the router. **This is expected, correct behaviour for the rule as written** (it is deliberately hostile to anything outside the admin subnet) and is exactly the lesson's own point; it just means this lab's commands must never be run as a `tools/conformance/` scenario over SSH (no scenario file was kept for it). If the lab is ever run against a real out-of-band-managed router by hand, always keep a console session open before adding the final `action=drop` rule.

## OSPF in the simulator

`src/lib/sim/ospf.ts` (engine) and `menus-ospf.ts` (CLI). Interfaces run OSPF when an address falls inside a template's `networks`; neighbours form across the layer 2 segment (same area, subnet, type, neither side passive); routes come from Dijkstra over interface costs (each router advertises the network of its OSPF interfaces at that cost, connected networks win) and appear as dynamic `DAo` routes with distance 110, gateway shown as `10.1.1.2%ether1`, scope 20. It converges instantly (real broadcast interfaces sit in "waiting" for about 40 s; use `type=ptp` for point-to-point links). The network's `epoch` (bumped by every command and cable) caches the result. Verified against the real routers by `tools/conformance/scenarios/ospf.json` (51 of 55 steps identical); known gaps: the sim takes the far end of a disabled port down like hardware, while GNS3 does not (so a real router still advertises the network behind a disabled port), `/routing route print`, `/routing ospf lsa`, areas other than the backbone in print detail, BFD sessions. The `ospf-triangle` lab is in `src/data/simLabsOspf.ts` (check kind `ospf-neighbors`); the routing lesson 04 uses it.

## BGP in the simulator

`src/lib/sim/bgpFilter.ts` (a small interpreter for the `/routing filter rule` script language: `if (dst == CIDR) { ... }`, `dst in`, `dst-len`, `bgp-communities any`, `set bgp-local-pref`/`bgp-path-prepend`/`bgp-communities`, `accept`/`reject`, default reject) and `bgp.ts` (engine: templates, connections, which sessions come up by matching each side's local/remote address and AS against the other's, best path by local-pref then AS-path length, distance 20 eBGP / 200 iBGP) plus `menus-bgp.ts` (CLI: `/routing bgp template|connection`, read-only `session`/`advertisements`, and `/routing filter rule`). **`/routing bgp connection` and `session` always print in a fixed block layout** (never a flat table, even without `detail`) where dotted properties fold to `.suffix` on repeats and each named GROUP (remote.\*, local.\*, the instance fields, output.\*, input.\*, and for a session two trailing scalar groups) always starts a fresh line - this is specific to these two commands and implemented as `renderGrouped` inside `menus-bgp.ts`, not the shared `renderBlocks`. A built-in `default` template (AS 65530) always exists, like on a real router. Verified against real eBGP between two routers: `tools/conformance/scenarios/bgp.json`, 31+ of 37 steps identical; the one open gap is `session print`'s `prefix-count`, which real RouterOS itself reported as both 0 and 1 across two otherwise-identical captures (a genuine timing race, not something to chase further). The `bgp-basics` lab is in `src/data/simLabsBgp.ts` (check kind `bgp-sessions`); routing lesson 01 uses it.

## WireGuard in the simulator

`src/lib/sim/menus-wireguard.ts` only - no separate engine file, because once a tunnel interface has an address it behaves like any other interface. The one real piece of engine work is in `network.ts`: `Network.peer()` now also resolves a **virtual link between two `wireguard` interfaces** whenever each side's peer names an address the other device actually owns (see `wireguardPeer()`) - a WireGuard tunnel is not a cable, it rides on whatever reaches the peer's endpoint, and the simulator does not model the handshake itself. `l2.ts`'s `segment()` had to learn that a `wireguard` interface (like `ether`) can originate and receive a frame directly, with no bridge underneath. Key pairs are fake but stable (deterministic per device+interface name, `fakeKey()`), MTU defaults to 1420. Verified against a real tunnel with a genuine handshake (captured each router's own generated public key first, then used the other side's real key so the real routers actually established): `tools/conformance/scenarios/wireguard.json`. Known gaps: `peer<N>` naming numbers from a global counter that keeps counting across captures (masked in comparisons), and the flat (non-detail) `peers print` truncates its own column headers on the real capture, which looks like an SSH terminal-width artifact rather than real RouterOS behaviour. The `wireguard-basics` lab is in `src/data/simLabsWireguard.ts`; mikrotik lesson 04 uses it.
